--------------------------------------------------------------------------------
01. WHAT IT IS
--------------------------------------------------------------------------------
A single-page-per-view app (no router, no SPA framework) for a water-bottle
distributor: create invoices, record payments, track customer pricing, manage
bottle-cap stock, and print A5 invoices. Every page is a standalone HTML file
that loads the same core scripts and calls Nav.render('page-name').

Offline-first by design — a delivery driver with no signal can still open the
app, create an invoice, and take a payment. Everything queues locally and
syncs when a connection returns.

02. STORAGE LAYERS
--------------------------------------------------------------------------------
Three different physical stores back the same logical key-value API
(DB.get / DB._set), chosen automatically by platform and data size.

  LAYER          USED WHEN                          NOTES
  -------------- ---------------------------------- --------------------------
  localStorage    Web build, default path            LZString-compressed on
                                                       write; namespaced wt_*
                                                       keys
  IndexedDB       A single key outgrows              Automatic overflow —
                  localStorage's quota                DB._set() migrates the
                                                       key transparently,
                                                       tracked in wt_idb_keys
  HDD (JSON       Desktop app, always                 Plain files in
  files)                                              %APPDATA%\...\data\ —
                                                       localStorage is left
                                                       empty on desktop
  DB._cache       Always, in front of all three       In-memory parsed cache
                                                       every read/write goes

03. SYNC ARCHITECTURE
--------------------------------------------------------------------------------
Every write flows the same direction — device first, cloud second — so the
app never blocks on a network round-trip.

  [localStorage]   [IndexedDB]   [HDD JSON]
   (web)            (overflow)    (desktop)
        \               |               /
         \              |              /
          v             v             v
                  [ DB._cache ]                 <- source of truth on-device
                        |
                        v
                 [ Sync layer ]                 <- sync.js + 4 CollectionSync
                        |                           modules
                        v
              [ orgs/{orgId}/... ]              <- Firestore
                        |
                        v
                [ Other devices ]                <- real-time listeners

Reads never block a save — the UI writes to DB._cache instantly and the
Firestore push happens debounced, in the background.

03.1  TWO SYNC SYSTEMS, SPLIT BY DATA SHAPE
--------------------------------------------------------------------------------
sync.js handles the transactional, high-volume data. Four purpose-built
modules own the master-data tables that need reliable add/edit/delete across
devices — the older whole-array approach couldn't do that reliably.

  DATA            OWNER                    FIRESTORE SHAPE          NOTES
  --------------- ------------------------ ------------------------ ------------------------------------------
  wt_invoices     sync.js  [COLLECTION]     invoices/{id}            One doc per record; 6-month rolling window
                                                                      synced live, older years fetched on demand
  wt_payments     sync.js  [COLLECTION]     payments/{id}            Same windowing as invoices
  wt_customers    customer-sync.js         customers_v2/{id}        Server collection is the single source of
                                                                      truth
  wt_products     product-sync.js          products_v2/{id}         Same pattern, built on the shared

  wt_pricing      pricing-grouped-sync.js  pricing_byproduct/{pid}  ~3,300 rules grouped into ~32 product docs

  wt_users        user-sync.js             users_v2/{id}            Pulled once, additively, before login is
                                                                      even possible
  settings,       sync.js  [DOCUMENT]       data/{name}              Whole object in one doc, field-path merged
  returns,
  versions, cap
  stock, price
  history,
  counters...

--------------------------------------------------------------------------------
03.2  READ-COST GUARDRAILS
--------------------------------------------------------------------------------
The project runs on Firestore's free tier, so read volume is treated as a
real constraint, not an afterthought. Current safeguards:

  - Session-guarded pull
      The expensive full sync only runs once per login, not on every page
      navigation.

  - Stable archive cutoff  [fixed v1.0.178]
      The invoices/payments listener window is rounded to the day, so
      re-opening pages doesn't re-bill a full read each time.

  - Diff-only writes
      Every collection fingerprints records before writing — unchanged rows
      never touch the network.

  - Delta cursor
      A 24-hour cursor lets a second same-day login fetch only what changed,
      not the whole window again.

  - Mass-delete guard
      A single write can't delete more than 5 records — blocks the failure
      mode that caused the June incident.

  - Grouped pricing docs
      3,300+ pricing rules read as ~32 documents instead of one each.

05. AUTH & PERMISSIONS
--------------------------------------------------------------------------------
Session lives in sessionStorage — gone the moment the tab closes, with a
12-hour hard cap either way.

  - Passwords       SHA-256 hashed; first login forces a change
  - Permissions     48 granular keys in Auth.PERMS — admin bypasses every
                    check automatically
  - Idle timeout    Configurable per-org (default 30 min), warns 2 minutes
                    out  [race condition fixed v1.0.179]
  - Mobile          Flagged users can be restricted to read-only on a phone,
    view-only       page access untouched
